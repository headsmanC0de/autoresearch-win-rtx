## 1. Що це за проєкт

**autoresearch** — це платформа для автоматизованих ML-експериментів, створена Андрієм Карпаті (ex-Tesla AI, ex-OpenAI).

**Ідея**: замість того щоб людина вручну правила код і запускала тренування, це робить AI-агент. Він:
- Змінює код моделі
- Запускає тренування на 5 хвилин
- Перевіряє чи стало краще
- Зберігає або відкочує зміни
- Повторює нескінченно

**Наш форк** (`autoresearch-win-rtx`) адаптований під Windows + споживчі GPU (RTX серія).

**Що ми тренуємо**: мініатюрну версію GPT (та сама архітектура що в ChatGPT), 50M параметрів, на датасеті дитячих оповідань (TinyStories).

## 2. Як влаштована нейромережа

### 2.1. Головна ідея — передбачення наступного слова

Всі сучасні мовні моделі (ChatGPT, Claude, Copilot) працюють однаково:

```
Вхід:  "The cat sat on the"
Модель: → "mat" (найімовірніше слово)
```

Модель бачить послідовність слів і намагається вгадати наступне. Повторюючи це мільйони разів на мільйонах текстів — вона "вчиться" мові.

### 2.2. Шлях тексту через модель

```
"The cat sat" (текст)
      │
      ▼
┌─────────────┐
│ Токенізатор │  "The cat sat" → [51, 2087, 1523]
│  (BPE)      │  Слова → числа (токени)
└─────────────┘
      │
      ▼
┌─────────────┐
│  Embedding  │  [51] → [0.12, -0.44, 0.87, ... ] (512 чисел)
│             │  Кожне число → вектор у 512-мірному просторі
└─────────────┘
      │
      ▼
┌─────────────┐
│Transformer 1│  Шари "думання" — кожен шар аналізує
│Transformer 2│  зв'язки між словами через механізм
│    ...      │  "уваги" (attention)
│Transformer 8│
└─────────────┘
      │
      ▼
┌─────────────┐
│   LM Head   │  Вектор → ймовірність кожного з 8192 слів
│             │  Обирає найімовірніше: "mat"
└─────────────┘
```

### 2.3. Що таке Attention (увага)?

Коли модель бачить "The cat sat on the ___", вона вирішує:
- Слово "cat" — важливе (підмет, хто сидить?)
- Слово "on" — важливе (де?)
- Слово "the" (перше) — менш важливе

Attention — це механізм що дозволяє кожному слову "дивитись" на всі інші і вирішувати що важливо.

### 2.4. Як модель вчиться (тренування)

```
Крок 1: Показати текст — "The cat sat on the ___"
Крок 2: Модель вгадує — "dog" (неправильно!)
Крок 3: Порахувати помилку (loss) — наскільки далеко від "mat"
Крок 4: Підкрутити ваги (backpropagation) — трохи змінити 50 мільйонів чисел
Крок 5: Повторити 57 разів за 5 хвилин (на нашій GPU)
```

**Loss** (помилка):
- Початок: ~5.7 (модель вгадує випадково, ніби кидає кубик)
- Кінець: ~2.5 (модель вже щось розуміє про мову)

### 2.5. Метрика якості — val_bpb

**val_bpb** = validation bits per byte.

Означає: скільки біт інформації потрібно моделі щоб закодувати 1 байт тексту.

| val_bpb | Що це означає |
|---------|---------------|
| ~4-5    | Випадкове вгадування (нетренована модель) |
| ~1.0    | Модель щось розуміє |
| ~0.8    | Непогано для 50M моделі за 5 хв |
| ~0.5    | Дуже добре (потрібна більша модель або більше часу) |
| 0       | Ідеальне передбачення (неможливо на реальних даних) |

**Чим менше — тим краще.**

Чому саме bpb, а не просто loss? Тому що bpb не залежить від розміру словника. Якщо ми змінимо кількість токенів з 8192 на 4096, loss зміниться але bpb залишиться порівнюваним.

## 4. prepare.py — лаборант

Цей файл запускається один раз (`uv run prepare.py`) і робить:

### 4.1. Завантажує датасет
- **TinyStories** — ~50,000 коротких дитячих оповідань, згенерованих GPT-4
- Зберігається в `%LOCALAPPDATA%\autoresearch\datasets\tinystories\`
- Розбитий на split-и: train (тренування), val (валідація), test (тест)

### 4.2. Тренує токенізатор (BPE)
- **BPE** (Byte Pair Encoding) — алгоритм що розбиває текст на підслова
- Розмір словника: **8192 токени**
- Приклад: "unhappiness" → ["un", "happiness"] (2 токени замість 1 слова)
- Зберігається як `tokenizer.pkl`

### 4.3. Фіксовані константи (НЕ змінювати!)

```python
MAX_SEQ_LEN = 2048    # Контекст: скільки токенів модель бачить одночасно
TIME_BUDGET = 300     # Бюджет тренування: рівно 5 хвилин
EVAL_TOKENS = 20.9M   # Скільки токенів для оцінки якості
VOCAB_SIZE = 8192     # Розмір словника токенізатора
```

### 4.4. Функція оцінки — evaluate_bpb()
- Прогоняє модель через валідаційні дані
- Рахує bits per byte
- Це "суддя" який вирішує чи стала модель кращою

### 4.5. Dataloader — подача даних
- Пакує документи в батчі без padding-у (100% утилізація)
- Кожен рядок починається з BOS (Beginning Of Sequence) токена
- Використовує best-fit алгоритм для ефективного пакування

## 5. train.py — серце експерименту

Файл ~1300 рядків. Ось його структура зверху вниз:

### 5.1. Runtime Configuration (рядки 38-300)
Автоматично визначає твою GPU і налаштовує параметри:

```
Твоя GPU: RTX 4070 Ti SUPER
├── Архітектура: Ada Lovelace (SM 8.9)
├── VRAM: 16 GB
├── AMP dtype: bfloat16 (точніше за float16, доступне на SM ≥ 8.0)
├── Профіль: ada-10-15gb
├── Batch size: 8 (підібраний autotune)
└── Activation checkpointing: enabled
```

**GPU Profiles** — передналаштовані конфігурації під різні GPU:

| Профіль | GPU | VRAM | Batch candidates |
|---------|-----|------|------------------|
| turing-8gb | RTX 2060/2070 | 8 GB | [8, 4, 2, 1] |
| ampere-10-23gb | RTX 3060/3080 | 10-23 GB | [16, 8, 4] |
| ada-10-15gb | RTX 4060Ti/4070/4070TiS | 10-15 GB | [32, 16, 8, 4] |
| ada-16gb+ | RTX 4080/4090 | 16+ GB | [32, 16, 8, 4] |

**Autotune** — при першому запуску пробує різні batch size і обирає найшвидший. Результат кешується.

### 5.2. Model Architecture — GPT (рядки 321-600)

```python
@dataclass
class GPTConfig:
    sequence_len: int = 2048   # Довжина контексту
    vocab_size: int = 32768    # (перевизначається з prepare.py = 8192)
    n_layer: int = 12          # Кількість transformer шарів
    n_head: int = 6            # Кількість "голів" уваги
    n_kv_head: int = 6         # KV-голови (для GQA)
    n_embd: int = 768          # Розмір embedding вектора
    window_pattern: str = "SSSL"
```

Компоненти моделі:
- **Embedding (wte)** — таблиця: кожному з 8192 токенів відповідає вектор з 512 чисел
- **Transformer Blocks (h)** — 8 шарів, кожен містить:
  - **Attention** — механізм уваги (дивиться на інші слова)
  - **MLP** — feedforward мережа (обробляє кожен токен окремо)
  - **RMSNorm** — нормалізація (стабілізує тренування)
- **LM Head** — перетворює вектор назад в ймовірності слів
- **Value Embedding (VE)** — додаткові learnable вектори через кожен шар
- **RoPE** — Rotary Positional Embeddings (кодує позицію слова в реченні)

**Sliding Window Attention** — патерн "SSSL":
```
Шар 1: S (short) — бачить 1024 токени (половину контексту)
Шар 2: S (short) — бачить 1024 токени
Шар 3: S (short) — бачить 1024 токени
Шар 4: L (long)  — бачить весь контекст 2048 токенів
```
Перші шари працюють з локальним контекстом (швидше), останній — з повним (потужніше).

### 5.3. Optimizer — MuonAdamW (рядки 600-790)

Гібридний оптимізатор:

| Тип параметра | Оптимізатор | Чому |
|---------------|-------------|------|
| Матриці (weights) | **Muon** | Ортогональні оновлення — зберігає геометрію градієнтів |
| Скаляри, embedding, bias | **AdamW** | Класичний, стабільний для малих параметрів |

**Muon** — новий оптимізатор, використовує QR-декомпозицію для ортогоналізації. Зберігає "напрямок" градієнта краще ніж Adam.

### 5.4. Training Loop (рядки 900-1360)

Спрощений псевдокод:

```python
start_time = time.time()

while time.time() - start_time < 300:  # 5 хвилин
    # 1. Взяти батч даних
    inputs, targets = next(dataloader)  # [8, 2048] токенів

    # 2. Forward pass — прогнати через модель
    loss = model(inputs, targets)       # Порахувати помилку

    # 3. Backward pass — порахувати градієнти
    loss.backward()                     # Як змінити ваги?

    # 4. Accumulate — зібрати градієнти з 32 міні-батчів
    if step % 32 == 0:
        optimizer.step()                # Оновити ваги
        optimizer.zero_grad()           # Обнулити градієнти

    # 5. Логувати прогрес
    print(f"step {step} | loss: {loss} | tok/sec: ...")

# 6. Evaluation
val_bpb = evaluate_bpb(model)
print(f"val_bpb: {val_bpb}")
```

## 7. Гіперпараметри — що крутити

### 7.1. Архітектура моделі

| Параметр | Поточне | Де в коді | Що робить |
|----------|---------|-----------|-----------|
| `DEPTH` | 8 | train.py:816 | Кількість transformer шарів |
| `ASPECT_RATIO` | 64 | train.py:799 | model_dim = DEPTH × AR (ширина моделі) |
| `HEAD_DIM` | 128 | train.py:800 | Розмір однієї "голови" уваги |
| `WINDOW_PATTERN` | "SSSL" | train.py:801 | Патерн sliding window attention |

**Формула розміру**: `model_dim = ceil(DEPTH × ASPECT_RATIO / HEAD_DIM) × HEAD_DIM`

Приклад: DEPTH=8, AR=64 → 512, поділити на HEAD_DIM=128 → 4 голови, dim=512

### 7.2. Оптимізація (learning rates)

| Параметр | Поточне | Що робить |
|----------|---------|-----------|
| `EMBEDDING_LR` | 0.6 | Швидкість навчання embedding шару |
| `UNEMBEDDING_LR` | 0.004 | Швидкість навчання вихідного шару (lm_head) |
| `MATRIX_LR` | 0.04 | Швидкість навчання основних ваг (Muon) |
| `SCALAR_LR` | 0.5 | Швидкість навчання скалярних параметрів |
| `WEIGHT_DECAY` | 0.2 | Регуляризація (запобігає перенавчанню) |
| `ADAM_BETAS` | (0.8, 0.95) | Momentum параметри Adam |

### 7.3. Батч і градієнти

| Параметр | Поточне | Що робить |
|----------|---------|-----------|
| `TOTAL_BATCH_SIZE` | 2^19 (524K) | Скільки токенів на один крок оптимізації |
| `DEVICE_BATCH_SIZE` | 16 | Скільки зразків за один forward pass (autotuned до 8) |
| `WARMUP_RATIO` | 0.0 | Розігрів LR на початку (0 = без розігріву) |
| `WARMDOWN_RATIO` | 0.5 | Частка тренування з зниженням LR |
| `FINAL_LR_FRAC` | 0.0 | Фінальний LR як частка від початкового |

### 7.4. Що безпечно міняти (для початку)

**Легко** (мало ризику зламати):
- `DEPTH` — кількість шарів (4, 6, 8, 12, 16)
- `ASPECT_RATIO` — ширина (32, 48, 64, 96, 128)
- `WINDOW_PATTERN` — патерн уваги ("L", "SL", "SSSL", "LLLL")

**Середньо** (може потребувати підстроювання):
- `MATRIX_LR` — learning rate (0.01 - 0.1)
- `TOTAL_BATCH_SIZE` — розмір батчу (2^16 - 2^20)
- `WARMUP_RATIO` — розігрів (0.0 - 0.1)

**Складно** (для досвідчених):
- Зміна архітектури моделі (GPTConfig, Block, CausalSelfAttention)
- Зміна оптимізатора (MuonAdamW)
- Додавання нових технік (dropout, різні нормалізації, тощо)

## 8. Як запускати експерименти


### 8.2. Запуск з логуванням

```powershell
# Перенаправити вивід у файл
uv run train.py > run.log 2>&1

# В іншому терміналі — спостерігати в реальному часі
Get-Content -Path "run.log" -Wait -Tail 20
# або через WSL:
tail -f run.log
```

```bash
# Головна метрика
grep "^val_bpb:" run.log

# Використання VRAM

# Все одразу
grep "^val_bpb:\|^peak_vram_mb:\|^mfu_percent:\|^num_steps:\|^num_params_M:" run.log
```

```powershell
# Вимкнути autotune (використати дефолтний batch size)

uv run train.py

# Перезапустити autotune (якщо змінив конфігурацію)
$env:AUTORESEARCH_AUTOTUNE_REFRESH = "1"
uv run train.py

# Примусово увімкнути/вимкнути activation checkpointing
$env:AUTORESEARCH_FORCE_CHECKPOINTING = "1"  # або "0"
uv run train.py
```

## 10. Автономний режим (агент)

### 10.1. Як це працює

```
Людина                          AI-агент
  │                                │
  ├── Редагує program.md ──────►   │
  │   (задає напрямок)             │
  │                                ├── Читає program.md
  │                                ├── Читає train.py
  │                                │
  │                                │  ┌─ LOOP FOREVER ─────────┐
  │   (спить)                      │  │ 1. Придумати ідею       │
  │                                │  │ 2. Змінити train.py     │
  │                                │  │ 3. git commit           │
  │                                │  │ 4. uv run train.py      │
  │                                │  │ 5. Перевірити val_bpb   │
  │                                │  │ 6. Keep або Discard     │
  │                                │  │ 7. Записати в TSV       │
  │                                │  └─────────────────────────┘
  │                                │
  ├── Прокидається ◄───────────    │
  │   Дивиться results.tsv         │
  │   ~100 експериментів готово!   │
```

### 10.2. Як запустити агента

1. Відкрити Claude Code / Codex / інший AI-агент в директорії проєкту
2. Написати:
```
Hi have a look at program.md and let's kick off a new experiment! let's do the setup first.
```
3. Агент запропонує тег (наприклад `mar13`), створить гілку, і почне працювати
4. Можна піти спати — агент працює автономно

### 10.3. Як зупинити

Просто закрити термінал або натиснути Ctrl+C. Результати вже збережені в `results.tsv` і git.

## 11. Git-воркфлоу

### 11.1. Структура гілок

```
master (основний код)
  └── autoresearch/mar13-depth-width (гілка експерименту)
        ├── commit: baseline
        ├── commit: exp1 DEPTH=4 (keep ✓)
        ├── commit: exp2 DEPTH=16 (discard ✗ → git reset)
        └── commit: exp3 DEPTH=12 (keep ✓)
```

### 11.2. Правила

- Кожен експеримент = окрема гілка від master
- Кожна зміна train.py = окремий коміт
- Якщо val_bpb покращився → **keep** (коміт залишається)
- Якщо val_bpb погіршився → **discard** (git reset до попереднього коміту)
- Результати записуються в `results.tsv` (TSV = tab-separated values)

### 11.3. Ручний воркфлоу

```bash
# 1. Створити гілку
git checkout -b autoresearch/mar13-my-experiment

# 2. Змінити train.py (наприклад DEPTH=12)
# ... редагувати файл ...

# 3. Закомітити
git add train.py
git commit -m "exp: try DEPTH=12"

# 4. Запустити
uv run train.py > run.log 2>&1

# 5. Перевірити результат
grep "^val_bpb:" run.log

# 6a. Якщо краще — записати і продовжити
# 6b. Якщо гірше — відкотити
git reset --hard HEAD~1
```

## 12. Типові експерименти

### Експеримент A: Глибина vs Ширина

**Питання**: Що краще — глибока вузька модель чи мілка широка?

```python
# Варіант 1: Shallow-wide (менше шарів, ширший dim)
DEPTH = 4
ASPECT_RATIO = 128  # dim = 512

# Варіант 2: Baseline
DEPTH = 8
ASPECT_RATIO = 64   # dim = 512

# Варіант 3: Deep-narrow (більше шарів, вужчий dim)
DEPTH = 16
ASPECT_RATIO = 32   # dim = 512
```

### Експеримент B: Window Pattern

**Питання**: Який патерн уваги працює найкраще?

```python
WINDOW_PATTERN = "L"      # Всі шари — повний контекст
WINDOW_PATTERN = "S"      # Всі шари — половина контексту
WINDOW_PATTERN = "SL"     # Чергування
WINDOW_PATTERN = "SSSL"   # Поточний (3 short + 1 long)
WINDOW_PATTERN = "LLLL"   # Всі long
```

### Експеримент C: Learning Rate

**Питання**: Який LR оптимальний?

```python
MATRIX_LR = 0.01   # Консервативний
MATRIX_LR = 0.04   # Поточний
MATRIX_LR = 0.08   # Агресивний
MATRIX_LR = 0.16   # Дуже агресивний (може розійтись)
```

### Експеримент D: Batch Size

**Питання**: Більший батч = менше кроків але точніші градієнти. Що краще?

```python
TOTAL_BATCH_SIZE = 2 ** 16   # 65K — маленький батч, багато кроків
TOTAL_BATCH_SIZE = 2 ** 19   # 524K — поточний
TOTAL_BATCH_SIZE = 2 ** 21   # 2M — великий батч, мало кроків
```

## Глосарій

| Термін | Пояснення |
|--------|-----------|
| **Token** | Шматочок тексту (слово або частина слова) |
| **Embedding** | Вектор чисел що представляє токен |
| **Attention** | Механізм що дозволяє токенам "дивитись" один на одного |
| **Transformer** | Шар нейромережі з attention + MLP |
| **Loss** | Помилка моделі (менше = краще) |
| **val_bpb** | Біт на байт на валідаційних даних (менше = краще) |
| **Learning Rate (LR)** | Наскільки сильно змінюються ваги за крок |
| **Batch** | Порція даних для одного кроку тренування |
| **Epoch** | Один повний прохід по всьому датасету |
| **Gradient** | Напрямок зміни ваг (отриманий через backpropagation) |
| **VRAM** | Відеопам'ять GPU |
| **MFU** | Model FLOPs Utilization — % від теоретичної швидкості GPU |
| **Checkpoint** | Збережений стан моделі (ваги) |
| **OOM** | Out of Memory — не вистачило VRAM |
| **BPE** | Byte Pair Encoding — алгоритм токенізації |
| **RoPE** | Rotary Position Embedding — кодування позиції токена |
| **RMSNorm** | Root Mean Square Normalization — стабілізація тренування |
| **Muon** | Оптимізатор з ортогональними оновленнями |
| **AdamW** | Класичний оптимізатор з weight decay |
| **GQA** | Grouped Query Attention — ефективніша увага |
